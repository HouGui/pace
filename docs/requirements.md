# Requirements and constraints

This document owns product behavior, setup and acceptance targets. These are acceptance targets, not claims of completion. Implemented behavior, tests and remaining gaps belong in [verification](verification.md).

## Baseline

One color calendar display using 2.4 GHz Wi-Fi, an existing calendar account and permanent USB power. Editing stays in the calendar app. Google Calendar uses the [hosted bridge](adapters.md#google-calendar); the optional Outlook service and custom adapters supply the same feed. The baseline requires no paid runtime subscription or extra always-on computer. The agenda remains visible outside the optional night schedule. See [design decisions](architecture.md#design-decisions).

## User interaction

### Installation and setup

Release packages should provide a browser installer using [ESP Web Tools](https://esphome.github.io/esp-web-tools/) and USB command-line instructions. Generate factory-image offsets from the target chip's build artifacts.

On first boot, show a QR code, temporary Wi-Fi name and random per-session password. The protected local wizard must support Wi-Fi credentials, Demo or a calendar endpoint/secret, time zone, locale, time format, temperature units, optional weather and category colors. Suggest browser preferences only on first setup; otherwise restore the saved configuration. Explain coordinate order and decimal notation with examples beside route and weather inputs. Preview settings before saving, explain connection/font errors, and close setup after success or inactivity. The user procedure lives in [device setup](development.md#device-setup).

Google bridge setup is a separate guided authorization/deployment step with no source edits. Explain account restrictions and alternatives; never require a public calendar. [Setup protection](ota-security.md#setup-protection) defines network and request safeguards.

### Calendar views and touch

Use the [screen concept](display-concept.svg) as a starting layout: today, a prominent next appointment, seven-day agenda and secondary temperature/weather-location/sync footer. Use dark text on a light background, separate category chips, labels and a legend; color must not be the only distinction. Group all-day events separately and subdue past events. FR-12–FR-14 own highlight, countdown and touch timing.

Show empty days explicitly and primary overflow as “+N more”; tapping opens the full list. When a second calendar is configured, show its count/label with an accent in week view, group its entries after main appointments in day view, and add an asterisk/accent to relevant month cells. The month legend names that source; its entries do not increase the main appointment count. Day navigation stays within loaded coverage. Month view uses a Monday-first grid with appointment counts, a today marker and adjacent loaded months; leap years and year boundaries must be correct. Unloaded dates are marked `--` and cannot be mistaken for empty days. Supplied adapters provide the current and following month within the bounded feed window; unrestricted historical/future browsing is outside this scope. Distinguish connection trouble, authorization errors, cached appointments and unavailable temperatures. Keep diagnostics in setup and explain unsupported scripts; full worldwide typography remains deferred.

Use a small Wi-Fi symbol with a check/cross for connection state; retain explicit text for faults. Traffic uses a compact four-card overview with readable times and tap-through details. Show a north-up OpenStreetMap street map with start/end markers for open routes; label approximate transit connections. The 256 × 160 viewport uses at most four 256-pixel PNG tiles, each ≤64 KiB. Fetch only the opened viewport, at most one tile per second, with a 10-second request deadline and 60-second error cooldown. Cache at most 16 tiles with a seven-day lifetime until eviction/reboot; decode one tile per UI iteration with bounded output. Keep attribution visible on the map. Map failure leaves journey details and calendar controls usable. Navigation, panning, offline downloads and live vehicle tracking are outside scope.

Display separate Inside/Outside temperature cards with prominent one-decimal values, source/age and missing/stale state. The reference enclosure uses a 180° GUI orientation with matching touch coordinates.

A deliberate settings hold reopens the wizard without reflashing. Confirm resets before deleting credentials/cache; updates require an explicit local action and follow [OTA recovery](ota-security.md). Normal setup and updates should work while mounted.

See [security profiles](ota-security.md).                                                                                                                                                                                                                               |

## Implementation constraints

| ID     | Constraint                                                                                                                                                                                                                                                                  |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CON-01 | Firmware uses C17/C++17, native ESP-IDF and FreeRTOS. Small JavaScript/Python supporting tools are acceptable.                                                                                                                                                              |
| CON-02 | Off-the-shelf modules; no custom PCB or mains circuitry. Exact reference parts are in the [BOM](../hardware/BOM.md).                                                                                                                                                        |
| CON-03 | Regulated supply, 3.3 V logic, ventilation and strain relief; measure electronics-induced sensor bias. Use a certified enclosed USB supply; leave the onboard battery connector unused.                                                                                     |
| CON-04 | Require distinguishable category colors and a roughly 7-inch readable display; do not mandate e-paper, LCD or a particular vendor. Isolate display/power details in board support. A different panel requires a validated driver and documented interaction/refresh limits. |
| CON-05 | The Google adapter keeps authorization upstream; the device holds only a revocable adapter secret. Provider quotas/deployment policy remain external dependencies.                                                                                                          |
| CON-06 | Public source contains no real appointments, credentials, private URLs, dumps or signing keys. Preserve dependency licenses.                                                                                                                                                |
| CON-07 | Prefer a factory-enclosed display and standard fasteners. No second outer case; a bare module may use one fitted rear cover. Keep electronics insulated, vents clear and mounting loads off glass/flex. No custom PCB or machined enclosure is required.                    |

## Deferred scope and open choices

Battery operation, calendar editing, unrestricted month-history queries, custom PCB, extra sensors beyond the indoor probe, MQTT/Matter, multi-household cloud management and additional providers beyond the supplied adapters are later options.

The reference design still needs fit, readability, thermal and delivered-cost validation. Record the panel revision and choose a signing-key custody/recovery process (OTA hosting is optional) before release. The implemented [local clock design](architecture.md#time-and-persistence) uses feed v2 offset segments. Universal font coverage is deferred.
